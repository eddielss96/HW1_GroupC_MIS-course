# 校園設備報修系統：Agent 工作規則

## 角色

你是本專案的 AI 開發 Agent，協助分析需求、修改程式與檢查結果。需求依據是 `software-spec.md`；不得自行發明規格書沒有要求的核心功能（例如登入、資料庫、刪除案件）。

## 開始修改前

1. 先讀取 `software-spec.md`，找出本次任務對應的功能編號（FR）與完成條件（AC）。
2. 沿著資料流找出受影響的檔案：`templates/*.html` → `static/*.js` → `app.py` → 回到前台與後台畫面。
3. 說明受影響的檔案、API 與預計修改方式，再開始修改。
4. 如果需求與規格矛盾、會改變狀態定義，或資料不足，先提出問題，不要自行假設。

## 開發規則

- 保持現有 API 路徑、回傳格式（`{"message": ..., "ticket": ...}`）與畫面流程一致。
- 所有輸入都必須在後端驗證；前端隱藏按鈕不能取代後端檢查。
- 修改狀態流程時，必須對照規格書的「案件狀態」表，檢查目前狀態是否允許轉換，以及由誰轉換。
- 「已取消」是終止狀態：任何 API 都不得把已取消案件改回其他狀態。
- 同一個功能必須同時檢查前台（`app.js`）與後台（`admin.js`）是否都正確顯示。
- 會造成無法復原結果的操作（例如取消報修）必須先讓使用者確認。
- 錯誤訊息使用繁體中文，並回傳正確的 HTTP 狀態碼（400、404）。
- 不得繞過驗證，也不得把未測試的結果寫成已完成。

## 完成修改後

1. 對照 `software-spec.md` 的完成條件，逐條確認。
2. 啟動系統（`.\.venv\Scripts\python.exe app.py`），實際操作前台與後台，並直接呼叫 API 測試錯誤情境。
3. 涉及狀態流程時，使用 `skills/status-change-review/SKILL.md` 進行檢查。
4. 依下列格式回報：

```text
修改檔案：
- ...

完成項目：
- FR-xx：...

測試結果：
- AC-xx：通過／未通過（說明）

尚未確認的風險：
- ...
```
