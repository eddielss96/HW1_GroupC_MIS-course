# 案件狀態變更檢查 Skill

## 使用時機

當任務涉及以下內容時使用本 Skill：

- 新增或修改案件狀態（例如取消報修、退回案件）
- 新增會改變 `ticket["status"]` 的 API
- 修改前台或後台的狀態顯示、按鈕或選單
- 設計狀態流程的測試案例

## 輸入

- 這次要新增或修改的狀態變更需求
- `software-spec.md` 的「案件狀態」表與完成條件
- 相關檔案：`app.py`、`static/app.js`、`static/admin.js`、`templates/*.html`

## 執行流程

1. **對照規格**：讀取 `software-spec.md`，列出本次變更的「原狀態 → 新狀態」、由誰觸發，以及對應的 FR／AC 編號。
2. **檢查後端**：在 `app.py` 找出所有會修改 `status` 的路由，確認：
   - 找不到案件時回傳 404
   - 原狀態不允許轉換時回傳 400 與清楚的訊息
   - 終止狀態（「已取消」）不能被任何路由再修改
3. **檢查前台**：在 `static/app.js` 的 `renderTickets()` 確認按鈕只在允許的狀態出現，且無法復原的操作有確認視窗。
4. **檢查後台**：在 `static/admin.js` 確認新狀態能正確顯示，不會被狀態選單誤顯示成其他狀態或被誤存。
5. **實際測試**：啟動系統，依下列情境操作畫面或直接呼叫 API：
   - 正常流程：允許的狀態轉換成功
   - 使用者在確認視窗按「取消」：不送出請求
   - 不允許的原狀態：回傳 400
   - 不存在的案件編號：回傳 404
   - 終止狀態再修改：回傳 400
6. **分類結果**：將每個項目歸類為「通過」、「需要修改」或「需要人工確認」。

## 輸出格式

```text
檢查結果：通過／需要修改／需要人工確認

狀態變更：
- 原狀態 → 新狀態（觸發者）

對應規格：
- FR-xx、AC-xx

受影響範圍：
- 後端：...
- 前台：...
- 後台：...

測試案例：
1. 前置條件：...
   操作：...
   預期結果：...
   實際結果：通過／未通過

需要人工確認：
- ...
```

## 不可忽略的事項

- 不得只在前端隱藏按鈕而省略後端狀態檢查。
- 不得自行更改規格書中原本的狀態定義或新增狀態。
- 不得用刪除資料取代狀態變更；取消的案件必須保留紀錄。
- 前台與後台必須都檢查，不能只改其中一邊。
- 不得把「需要人工確認」或未實際測試的項目說成已完成。
